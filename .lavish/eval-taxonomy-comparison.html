A

Two-Axis: Scope × Method

Every eval is classified on two independent axes: scope (what behaviour is tested) and method (how the check runs). The analysis keeps its scope codes, the plan's tiers become methods, and phase labels are dropped from scripts.

Strengths

  • • Clean separation — always know what and how
  • • Existing analysis codes survive as-is (just the scope axis)
  • • Makes gaps precise: "happy-path × LLM-judge for implement_change"
  • • Naturally extensible — new methods or scopes add rows/columns

Weaknesses

  • • Two-dimensional — harder to reference quickly ("the structural happy-path eval")
  • • Most cells are empty — matrix is sparse
  • • Analysis tables need a new column rather than a simple rename
  • • Biggest refactor of the three approaches

Example: open_story refinement quality → scope: happy-path · methods: structural (12 sections present) + llm-judge (what_not_how score)

B

Single Flat Taxonomy

Merge everything into one flat list of 6 eval types. Each type has a clear name, cost, and script location. Drop the tier/phase language entirely.

Type Cost Script layer Replaces
guardrail free check_guardrails.sh STATIC_GUARDR
structural free *_golden_quality.sh T1 section EX-SIDEFX + EX-OUTPUTQ (deterministic parts)
quality-judge moderate *_golden_quality.sh T2 section EX-OUTPUTQ (quality parts) + T2
functional high *_golden_quality.sh T3 section T3 (new)
edge-case moderate *_dirty_state.sh, *_not_on_main.sh EX-EDGE + EX-FAIL
gate-block moderate *_blocks_on_gate_failure.sh EX-BLOCKINGGT

Strengths

  • • Simplest to explain and reference — one word per eval type
  • • Each scenario file tagged with its type(s)
  • • Analysis tables use the same names as the scripts
  • • Smallest refactor — mostly renaming

Weaknesses

  • • Mixes scope and method — "quality-judge" is both
  • • Less precise gap analysis ("missing a structural" says less than "missing happy-path × structural")
  • • "edge-case" lumps EX-EDGE and EX-FAIL together

Example: open_story refinement quality → types: structural + quality-judge

C

Independent Layers

Keep the plan's tiered structure but extend it to cover all eval types with stable, descriptive names. Each layer is independent — they can run in any combination. Ordered by cost for convenience, but there's no dependency between them. The analysis tables get a layer column instead of type codes.

Layer Name Cost Runs Replaces
L0 guardrail free always · check_guardrails.sh STATIC_GUARDR + Phase 1
L1 structural free always · in golden_quality.sh T1 + EX-SIDEFX (deterministic)
L2 judge moderate when EVAL_JUDGE_MODEL set T2 + EX-OUTPUTQ (quality)
L3 functional high when EVAL_T3=true + Android SDK T3 (new, build/test)
L4 behavioural moderate dedicated scenario scripts EX-EDGE + EX-FAIL + EX-BLOCKINGGT

Strengths

  • • Preserves the plan's tier intuition (T1→L1, T2→L2, T3→L3)
  • • L4 gives edge/gate/failure scenarios a proper home
  • • Easy to reference: "we're missing L3 for implement_change"
  • • Each layer is independent — mix and match per scenario

Weaknesses

  • • L4 "behavioural" is a catch-all — lumps edge cases, gate failures, and failure handling
  • • Analysis table needs a layer column (the 7 codes merge into 5 layers)

Example: open_story refinement quality → L1 (12 sections present) + L2 (what_not_how score)  ·  verify_story build gate blocks → L4 (gate-failure scenario)
