Acceptance Criteria Expansion

The story was expanded from 3 to 9 acceptance criteria, covering the full feature scope:

  • User can tap Navigate button on a specific leg segment in the route
  • Navigate button is only visible when a route is complete and the leg has both origin and destination
  • Tapping Navigate launches Google Maps directions from origin to destination
  • The directions URL includes both origin and destination coordinates
  • Error handling when no navigation app is available shows appropriate message
  • Navigation works with all stop types (starting point, intermediate, destination)
  • The feature respects system navigation app availability
  • User is returned to the trip detail view after selecting a navigation app
  • Analytics event navigation_launched is emitted with leg position and stop type

Feature Distinction from 5.1.1

This story is deliberately distinguished from Epic 5 Feature 5.1.1 (Navigate to Stop), which uses a single-point geo: URI for a stop location. Story 5.1.2 enables leg segment navigation using Google Maps directions URLs with both origin AND destination coordinates. This provides turn-by-turn routing between two points on the trip, rather than navigation to a single stop. The key design decision: Google Maps directions URLs are the only option that shows both origin and destination, making them essential for leg navigation use cases.

MVI Architecture

Defined MVI artefacts for the feature:

  • Intent: OnNavigateLegClicked — fired when the user taps Navigate on a leg
  • Effect: LaunchLegNavigation — carries origin/destination coordinates and triggers the intent
  • Reused Effect: ShowNavigationError — handles cases where no navigation app is available

Propose Change

5 Oct 2026, 13:41:07 UTC

Source: sdlc_propose_change

Exploration Summary

Architecture

  • NavigationUriBuilder.kt has buildGeoUri() for single-stop navigation (5.1.1). Needs new buildDirectionsUrl() method.
  • LegSummary.kt is a simple Row composable with distance/duration. No interactive elements currently.
  • TripDetailViewModel handles navigation via navigateToStop() pattern with allStops building, analytics logging, and effect emission.
  • MainScreen.TripDetailEffectHandler consumes navigation effects with resolveActivity/startActivity pattern.
  • Leg domain model has fromStopId/toStopId but no coordinates — must look up from Stop model.
  • Existing LegSummaryTest has legSummary_exposesNoClickableSemantics that will break when button is added.

Key Risks

  • Package visibility on API 30+ for resolveActivity with https URLs
  • Three LegSummary call sites in TripDetailScreen must all be updated
  • Row height will increase with IconButton (48dp touch target)

Questions Asked and Answers Received

QuestionAnswer
Should leg navigate button be disabled/hidden for VISITED stops? Always enabled — disabled only during isLoading. Even VISITED stops can be re-navigated as legs.
How to handle resolveActivity on API 30+ for https URLs? Use try-catch with startActivity directly, catch ActivityNotFoundException. No resolveActivity needed, no manifest queries change.
How should content descriptions be provided to LegSummary? ViewModel precomputes a Map<String, String> of content descriptions keyed by fromStopId in UiState.
